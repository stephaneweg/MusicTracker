Big feature (HISTORICAL): replace/augment the linear sequencer with a **graph-based composition** mode — drag&drop module boxes connected to control the flow of music.

**Agreed design decisions (2026-06-10):**
- A "play riff" module triggers its output connections **when the riff finishes** (sequential handoff). Multiple outputs from one node fire **simultaneously** → parallel branches. Layering = branching from a common node (e.g. Tempo → riffA + riffB + riffC at once), not chaining.
- **Unified "Repeat" module**: a `body` output (run N times, or infinite loop) + a `next` output (fires after the N repeats). Covers "repeat N", "loop forever", "repeat N then play that".
- **Parameter modules (e.g. Set Tempo)**: an execution context (tempo…) flows DOWN each branch and is **copied at forks**, so it affects descendants but not siblings.
- Modules: Start, Play Riff, Pause(x), Set Tempo, Pitch Shift, Repeat.
- **Pitch Shift module** (`PitchShiftModule.Semitones`): like Tempo, the value flows down the branch (copied at forks). At playback, multiply the riff's note frequencies by 2^(Semitones/12) — implement as a `FrequencyModifierWaveFunction` wrapping the riff instrument. Stacked pitch modules on a path ADD their semitones (factors multiply); the runtime context should accumulate semitones.
- A **Riff** = one polyphonic sequencer layer + instrument; **shared/reusable** (e.g. a recurring chorus). Tempo is NOT in the riff — it comes from the graph.

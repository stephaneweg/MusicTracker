Ongoing goal (stated 2026-06-09): the author wants to procedurally generate realistic acoustic instrument timbres (e.g. a violin with attack/sustain/release), not just raw synth waveforms.

Recipe used: **source** (sawtooth = bowed-string Helmholtz motion) → **body resonances/formants** (fixed-Hz Peaking filters) → **bow noise** → **ADSR** → headroom attenuation.

First milestone delivered: added `BiquadFilterWaveFunction` (RBJ cookbook biquad: LowPass/HighPass/BandPass/Peaking/Notch) in `Engine/WaveFunction.cs` — the engine previously had **no filter at all**, which was the key gap for acoustic realism. Plus `Engine/WaveFunctionPresets` with `Create(name)` for a "Generate >" menu (Violin/Piano/Oboe/Flute/Clarinet/Guitar/Brass/Organ) in both instrument editors.

MuseScore import: `Engine/MuseScoreImporter.cs` reads `.mscz` (zip) / `.mscx` (XML), maps each staff to its embedded GM program (`<Part>/<Instrument>/<Channel>/<program value>`), walks `<Measure>/<voice>/<Chord|Rest>` accumulating ticks (24 slices per quarter, like the MIDI import), and the sequencer "Import MuseScore" menu builds one layer per staff via `CreateForGmProgram`. Note index = MIDI pitch − 12 (slice index 0 == MIDI 12, matching `Utils.Frequencies`); the older MIDI import uses pitch directly (octave-high, not yet fixed). Needs csproj refs System.IO.Compression(+FileSystem). Verified on Ninna d'Anna (v3): 221 notes, violin→GM40, piano→GM0.
- **MuseScore 2 supported too (same menu, transparent).** Differences handled: MuseScore 1/2 put `<Chord>`/`<Rest>` directly under `<Measure>` (no `<voice>` wrapper) — importer falls back to treating the measure as the voice when no `<voice>` children exist. **Tuplets** are now handled (both versions): a `<Tuplet id=N>` definition (normalNotes/actualNotes) followed by chords with a `<Tuplet>N</Tuplet>` reference → duration scaled by normalNotes/actualNotes. A `.mscx` can contain multiple `<Score>` (main score + linked-part excerpts that duplicate the notes); we read only the first `<Score>` via `.Elements()` (direct children), which is the complete main score. Verified on Wait_There (v2): 1691 notes (oboe→GM68 + piano), 89 measures, slice count aligns. Still no tie merging / repeat expansion.

GM milestone: `WaveFunctionPresets.CreateForGmProgram(0..127)` returns a procedural template for every General MIDI program (family-based parametric generator: 16 families of 8), plus `GmName(p)` for the standard names and `CreateDrumKit()`. The sequencer MIDI import (`Screens/SequencerScreen.xaml.cs`, `menuImportMIDI_Click`) now assigns these templates on PatchChange (instead of the old AudioPatch SoundFont lookup), maps MIDI channel 10 to a drum kit, and defaults patch-less tracks to piano. All 128 verified finite and bounded (peak |sample| ~1.07). Known limit: one instrument per layer, so drum channel can't map each note to a distinct sound.

**Architecture note (instrument = node tree):** a saved instrument is a `WaveFunction` COMPOSITE TREE — a final node with source WaveFunctions cascading down to primitives. This is the right, idiomatic model (modular-synth style) and is sound. Main structural limitation: it's a TREE, not a DAG — a node's output can't be SHARED/fanned-out to multiple parents (e.g. one LFO driving both vibrato and amplitude needs two LFO instances). Evolve to a DAG (nodes by id, evaluated once/sample) only if shared-modulation is ever needed. The instrument-editor node controls (`Controls/InstrumentEditor/*`) now use a 3-column layout (input ports left / box / output port right) with ports OUTSIDE the box and graph-style colors (green output, blue input, green link), matching `Controls/Flow/FlowModuleControl`.

**How to apply / engine conventions to respect:**
- A `WaveFunction` is sampled via `GetCurrent(freq, sampleRate, modulatorValue)` then `MoveNext()`. Keep `GetCurrent` side-effect-free and advance internal state (counters, filter history) only in `MoveNext` — that's why the biquad defers its history shift to MoveNext.
- **Oscillators now derive from `OscillatorWaveFunction`** (Sine/Square/Triangle/Sawtooth): implement `Sample(double phaseInCycles)`. They integrate frequency into an accumulated phase (in MoveNext) instead of `frequency*T/SampleRate`, so time-varying frequency (vibrato/glissando) is correct. Don't reintroduce `f = frequency*T/SR`.
- **CRITICAL — `Ended` must propagate UP through wrapper nodes.** The ADSR decides when a voice's envelope is done (sets its own `Ended=true` at end of release). Wrappers (`AmplitudeModifier`, `FrequencyModifier`, `Vibrato`, `BiquadFilter`, `FrequencyModulation`, `Add`, `Multiply`) now set `Ended = child(ren).Ended` at the END of their `GetCurrent` (Add/Multiply: both children ended; FM: carrier ended) so the TOP node's `Ended` reflects completion. Without this, a voice's root `Ended` never became true → the flow `RiffPlayer` never detected the riff as finished → chained riffs never transitioned ("start→riff→riff plays nothing after the first"). The sequencer masked it (loops + retriggers via TRelease). Don't remove these pull-ups.
- **CRITICAL — consumers must drive a WaveFunction with `GetNext` (GetCurrent + MoveNext), once per sample.** Oscillators/filters now hold internal state (phase, IIR history) that only advances in MoveNext. The old `SequencerWaveProvider`/`Choord` pattern of setting `WaveFunction.T` by hand and calling `GetCurrent` on a SINGLE shared instance across all 96 notes produced SILENCE after phase accumulation (sine stuck at phase 0). Fixed by giving `SequencerWaveProvider` one cloned **voice per note** (`WaveFunction[] voices`), each driven by `GetNext` — this also makes biquad filters work per-voice in the sequencer. Any new polyphonic consumer must use per-voice instances + GetNext, never shared-instance T-swapping. (`Choord` is dead code and still uses the old broken pattern.)
- **Audio must run off the UI thread.** The sequencer screen used `WaveOut` created on the UI thread → NAudio filled buffers (the heavy synthesis) via window callbacks ON the UI thread → the playback cursor/display lagged. Fixed by using `WaveOutEvent` (background-thread buffer filling) and marshalling the `SelectNote` cursor-follow callback to the UI thread via `Dispatcher.BeginInvoke` (it's now invoked from the audio thread). Done: `SequencerLayerWaveProvider.Read` now reuses a persistent `double[][] mixBuffers` (reallocated only when layer count or sampleCount grows) instead of allocating a List + double[] per layer every call — less GC pressure on the audio thread. If audio (not display) still glitches on very dense passages, the remaining optimization is to pre-clone a voice pool instead of JSON-cloning on each note-on.
- **Voice mixing: SUM, don't average.** `SequencerWaveProvider.ReadNext` returns the SUM of active voices (not `total/cpt`). Dividing by the active-voice count made each new note quieter while earlier release tails were still sounding (a piano melody ducked itself note after note — "stuck in decay"). The output is instead clamped to [-1,1] in `SequencerLayerWaveProvider.Read` (the `(short)` cast wraps on overflow, so clamping is required).
- **`modulatorValue` is a phase offset in CYCLES** (1 cycle = one period), interpreted identically by every oscillator. FM/PM depth is set by scaling the modulator's amplitude.
- **`AmplitudeModifier` allows gain > 1** (clamped only to >= 0): it doubles as a modulator-gain / FM-index control, not just an attenuator.
- **`AddWaveFunction` is a normalising mixer** (divides by total volume), intentionally — keeps the final signal in [-1,1]. It is NOT a raw sum.
- Vibrato (`VibratoWaveFunction`): `VibratoFrequency` is a depth ratio (fraction of pitch), `VibratoSpeed` in Hz. It modulates frequency for real and propagates the upstream modulatorValue.
- ADSR releases from the level reached at release time (not from sustain) and release works during attack/decay.
- Changing the modulatorValue unit convention re-tunes any FM/vibrato instrument in userdata.json (Violin #1 vibrato was retuned to depth 0.02 / 5.5 Hz; Snare #5 has a sine-carrier FM that is now deeper).
- **Engine sample rate is CENTRAL: `Engine.AudioFormat.SampleRate` (= 22050 Hz).** Used everywhere — every WaveProvider16 subclass's WaveFormat (FlowPlayer, LoopingRiffProvider, SequencerLayerWaveProvider, TrackWaveProvider, InstrumentWaveProvider all pass `base(AudioFormat.SampleRate, 1)`), every `GetCurrent/GetNext` rate arg, every `Interval = …*rate`, the WaveExporter (WAV/MP3 export rate), and the FlowPlayer/RenderFlow calls in MusicScreen. `AudioPatch.TargetSampleRate = AudioFormat.SampleRate`. 22050 matches roland.sf2's native rate (no resampling) and halves synth CPU/RAM. To change the whole app's rate, edit ONLY `AudioFormat.SampleRate`. (Was 44100 hardcoded in ~20 places.) Also `AudioFormat.OutputGain = 0.5` (−6 dB): applied at the final mix stage (before clamp) in EVERY output provider's Read (FlowPlayer, SequencerLayerWaveProvider, LoopingRiffProvider, InstrumentWaveProvider, TrackWaveProvider) so summed voices/layers don't clip/saturate — in playback AND export (export reads these same providers). Adjust the headroom via that one constant.
- **SoundFont samples: 32-bit float pipeline + load-time resample to the engine rate (THE real quality fix).** `Engine/AudioPatch.LoadSoundFont` resamples each unique sample to `AudioPatch.TargetSampleRate` (= `AudioFormat.SampleRate`, the engine's output rate) ONCE at load, via `ResampleSegment`/`CatmullRom` (cubic Catmull-Rom interp), cached by the sample's global start offset (`Dictionary<int,ResampledSample>`). Each `AudioPatchPart.doubles` is now a per-sample 0-based 44100 Hz buffer with `SampleStart=0`, `SampleEnd=len`, loop points rescaled by the ratio, `SampleRate=TargetSampleRate`. **Why this matters:** SF2 fonts store samples at their native rate — e.g. roland.sf2 (the one loaded) has 492/496 samples at **22050 Hz**, none at 44100. The old code shared one big buffer and resampled on EVERY output sample at playback (`sr = SampleRate/outputSR = 0.5`) with linear interp → every note up-sampled ×2 live → dull/aliased vs Windows. Now playback runs at `sr≈1`: a note at its root pitch reads the buffer 1:1 (NO interpolation), only transposed notes interpolate, and the one-time resample uses higher-quality cubic. Verified: 22050→44100 doubles the length, loop points scale (50→100, 200→400), peak stays ~1.0, and a 44100 sample is passed through bit-exact (identity). **The bit-depth angle was a red herring for these fonts** (none have an `sm24` chunk → all 16-bit); the sample RATE was the culprit. Supporting infra kept anyway: `SoundFontSampleData` reads `smpl`+optional `sm24` into a normalized `float[]` (24-bit when present, else 16-bit); `SoundFont.waveData`/`WaveData`/`WaveDataArray` and `AudioPatchPart.doubles` are `float[]`; `AudioPatchWaveFunction.GetCurrent` reads them directly (NO `/32768.0`). Don't reintroduce a `/32768`, a `short[]` sample buffer, or share the whole font buffer across parts (breaks the 0-based per-part indexing). CLEANUP (removed): the legacy JSON-patch system is GONE — the `AudioPatch\*.txt` files + folder, the static-ctor `Directory.GetFiles("AudioPatch")` load, and the `AudioPatchPart.Serialized`/`bytes`/`serialized` base64 deserialization were deleted; `AudioPatch` now loads ONLY the SF2. `roland.sf2` (the sole loaded font) was moved INTO the project source + csproj (it had existed only in bin\Debug → a clean/clone lost the sound). Unused fonts FluidR3/SGM/Generam/TimGM left in place per the user. The MeltySynth SF2 parser IS required (NAudio doesn't parse SF2). It was EXTRACTED into its own project `MeltySynth` (repo-root `MeltySynth\`, old-style net48 class library, GUID 6F3A1C2B-…, added to MusicTracker.sln; MusicTracker references it via ProjectReference). It only needed `ReadString`/`ReadInt16s` from MusicTracker.Extensions → now a self-contained `MeltySynth/IoExtensions.cs` (the `using MusicTracker;` lines were stripped). `Properties/AssemblyInfo.cs` has `[InternalsVisibleTo("MusicTracker")]` so AudioPatch can still read `SoundFont.WaveDataArray` (internal). It references System.Memory/System.Buffers/System.Numerics.Vectors/System.Runtime.CompilerServices.Unsafe (for `Span<>`) via ..\packages HintPaths. Build verified: MeltySynth.dll compiles, MusicTracker links it.

- **Drum patches are ONE-SHOTS** (`AudioPatchPart.OneShot`, set `=isDrum` in LoadSoundFont, which also zeroes the drum loop points). In `AudioPatchWaveFunction.GetCurrent`, when `index >= size` a OneShot part sets `Ended=true; return 0` instead of `index%size` (wrap). Without this, a held drum note (a riff hit lasts ≥1 slice — long at slow tempo) loops/wraps the sample → sustained "long note" / machine-gun. Now the hit length = the sample's natural length (short), independent of tempo, while spacing stays tempo-driven. Non-OneShot (pitched) playback is unchanged (still wraps). Drum hits in DrumPattern are also 1 slice (`HIT=1`).

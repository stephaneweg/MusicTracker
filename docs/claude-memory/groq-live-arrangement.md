**Goal (user, 2026-07-01):** now that the user has a Groq API interest, generate music via a LIVE LLM call instead of (only) the pre-authored theme catalog. User's framing: ask Groq "génère une mélodie portée1[instrument, note:durée…], de telle forme, X mesures de thème + N variations, intro/mélodie/contrechant/accompagnement, dans le style de (compositeur/style/humeur/genre)", MusicTracker parses the reply into the timeline.

**Decisions (AskUserQuestion, 2026-07-01):** (1) **Niveau 2** = Groq generates the WHOLE arrangement (all staves + sections), not just a seed theme for the engine to develop. (2) **In-app** = a "Générer via IA (Groq)" path inside the app (button/model in CreateStructureDialog), not an offline script.

**Key architectural insight:** `ComposeResult` (Engine/Timeline/MusicComposer.cs) is the UNIVERSAL contract the timeline consumes via `TimelineScreen.ApplyComposeResult`. So the Groq generator = a new `MusicComposer` subclass whose `Compose(ComposeContext)` calls Groq, parses, validates, and fills a `ComposeResult` — **zero timeline changes**, same path as everything else (`dialog → ChosenComposer.Compose(ctx) → ApplyComposeResult`). Reuses: `ThemeLibrary.ParseMelody(mel,spq)` (token melody `"<midi>/<dur>"`, '|'=bar sep, 'r'=rest, '+'=chord → whole-piece absolute Starts) + `MusicComposer.AddBarRiffs(tracks,gm,name,fullRiff,totalBars,barSlices,riffs)` (protected static, splits a full line into one riff/bar) + `ChordCell(root,quality)` + `ArrSection(name,role,startBar,bars)` + `ComposedArrangement`. CRITICAL grid rule: ParseMelody accumulates the cursor CONTINUOUSLY and treats '|' as a mere separator → **each bar MUST sum to barSlices** (barSlices = num*(4*spq/den); 4/4=96) or the whole line drifts — hence the validator.

**JSON contract (LLM output):** one object = {title, style, mood, tempo, key{tonicPc,minor}, meter{num,den}, spq:24, totalBars, sections[{role,name,startBar,bars}], chords ("root:quality | …" one per bar, quality = PatternGenerator idx 0..22), tracks[{role(melody|counter|accomp|bass), name, gm(GM program), notes(full-piece token melody)}]}. Same token format as the .mscx scripts + theme catalog → the catalog serves as FEW-SHOT in the prompt (like `generate_themes.ps1` did for Anthropic).

**Groq specifics:** OpenAI-compatible. Endpoint `https://api.groq.com/openai/v1/chat/completions`, header `Authorization: Bearer <key>`, body = OpenAI `messages` (NO Anthropic `thinking` block), parse `choices[0].message.content`. .NET 4.8 caveats: HttpClient + `ServicePointManager.SecurityProtocol |= Tls12`. Free tier (no card) at console.groq.com/keys — this REMOVES the blocker that killed the old Anthropic "Phase D" (user wouldn't create an Anthropic org/key; see [[theme-library-seed-engine]] Phase D ABANDONED). Key stored in AppSettings (like StructureSettings), never hardcoded.

**Prior art already built (retarget, don't rewrite):** repo-root `generate_themes.ps1` = the exact "LLM theme factory" (schema+idiom+few-shot prompt → API → extract JSON → validate via `validate_themes.ps1` → re-prompt with errors/retry). The Groq path reuses this shape (prompt+validate+repair loop), just OpenAI endpoint + full-arrangement schema (multi-track) instead of a bare seed theme.

**Honest risk (the crux):** open-weight models on Groq (Llama etc.) are weaker than Claude at coherent symbolic music (in-key, bar sums, voice-leading) → the C# validator + few-shot + repair loop are what make a "dumb" source usable. KEEP the catalog: it's ear-validated + is the few-shot + is the fallback. Cache good generations back into the catalog → it grows itself (Phase 4).

**Phasing:** P1 offline core (DTOs+parser+C# validator) · P2 GroqClient + AiComposer (prompt + validate/repair) + FIRST LIVE CALL (judge quality = the real go/no-go for Niveau 2) · P3 UI (dialog entry + key/model settings + wait cursor) · P4 cache to catalog.

**LIVE EXPERIMENTS (2026-07-01, 3 calls, key provided) — KEY FINDINGS:**
- Groq is OpenAI-compat & FAST (~3s). Models: llama-3.3-70b-versatile, llama-3.1-8b-instant, openai/gpt-oss-120b & 20b (REASONING — hidden thinking tokens count vs the budget), qwen3-32b, llama-4-scout, etc. (GET /openai/v1/models).
- **FREE TIER TPM CAP** = the real constraint. gpt-oss-120b free tier = **8000 tokens/min**, and Groq returns **HTTP 413 "Payload Too Large"** (not 429) when `prompt_tokens + max_completion_tokens` > TPM. Error body `.ErrorDetails.Message` states the limit. So a big reasoning model can't do a full piece per call on free tier. llama-3.3-70b has a higher TPM (2764-token calls succeeded) → the workhorse. Dev tier (paid) lifts this.
- **FORMAT: solved.** llama-3.3-70b returns valid JSON in the exact schema, right chord qualities (color: 6/add9/Maj9), correct chord count, ~3s.
- **MELODY QUALITY: bad WITHOUT few-shot** (it output a literal ascending C-major SCALE incl. the avoided 4 & 7, looped an octave up — an exercise, not a tune). **GOOD WITH few-shot** (fed 2 real ghibli.json 4/4 theme melodies as examples + an explicit "INTERDIT: pas de gamme; sauts + rythme varié + phrases qui respirent"): produced real expressive lines (leaps, mixed quarter/eighth/half, phrase-ending long notes) for BOTH melody and counter. → the catalog earns its keep as FEW-SHOT.
- **ARITHMETIC: the LLM's weak spot.** With expressive rhythm it stops summing bars to barSlices (bars at 144/120/48). LLMs can't reliably count slices. FIX = engine-side, NOT prompt-side: a TOLERANT BAR-AWARE parser that treats '|' as a HARD bar boundary (each bar restarts at bar-start, cumulative length CLAMPED to [0,barSlices], overflow clipped/dropped, underflow = trailing gap, bar count padded/truncated to totalBars) → any LLM output becomes renderable, arithmetic errors stay LOCAL (don't cascade). NB ThemeLibrary.ParseMelody does the OPPOSITE (continuous cursor, '|' ignored) so it must NOT be reused for LLM output — write a new bar-aware parser.
- **ACCOMP/BASS: LLM does it badly** (same C arpeggio every bar, ignores the chord grid; or parallel gliding triads). The ENGINE already renders these perfectly from the chord grid (MakeBacking / RenderMotifOverProgression). → don't ask the LLM for them.

**DECISION (AskUserQuestion, 2026-07-01): HYBRID (refines the earlier "Niveau 2").** Groq generates form + chords + **melody + counter** (the creative top voices, few-shot-guided); the ENGINE renders **accomp + bass** from Groq's chord grid (reuse existing machinery) and does the tolerant bar-parse + polish. Best quality, less LLM-arithmetic fighting, reuses the validated engine. (Full-LLM-everything and "try gpt-oss-120b first" were the other options; hybrid won.)

**CRITICAL FORMAT FIX (2026-07-01): musical duration CODES, never "slices".** First full-AI test (Chopin) had EVERY bar wrong because the prompt was AMBIGUOUS — it said both "4=noire" AND "chaque mesure = 96 slices / 8t=8" → the model MIXED conventions (melody used codes /16 /8, accomp+bass used slices /24 /96). Fix = prompt speaks ONLY in note values (1=ronde,2=blanche,4=noire,8=croche,16=double,+"."/"t"), states "1 ronde = 4 noires = 8 croches", gives a worked example bar, and FORBIDS non-{1,2,4,8,16,32} numbers + the word "slices". The parser (AiArrangementValidator.DurToSlices, code-based) then matches. RESULT (re-test, Chopin/Nocturne/Am, generic few-shot): accomp 16 bars/0 errors, bass 16/0, melody 6/16 residual, counter 18 bars → all absorbed by the tolerant parser. Also added a "distinct idiomatic GM per voice" nudge (was all gm=0/piano). ~2.5-3.7s, ~900-1350 out tokens (well under llama TPM).

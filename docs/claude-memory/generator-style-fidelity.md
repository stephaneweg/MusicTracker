Goal (2026-06-19): make GENERATED melody (pitch AND rhythm) sound more like the trained model's style.

**USER VERDICT (2026-06-19): the Markov/model generation sounds BAD to the ear — "random", worse than even the Mathematical generator.** Root cause = no macro STRUCTURE (motif, repetition, phrase arc, goal-directed harmony); low-order Markov = locally-plausible-but-aimless random walk; the math generator wins because it HAS structure/self-similarity. NO amount of better local stats fixes "no structure." **Core lessons for #1:** (1) *enriching the melody by sampling the model MORE makes it WORSE* — more degrees of freedom = more drift, because the model has no notion of "this is THE motif, vary IT", it only predicts the next local note. (2) The fix is **enrich = bounded transformation of a FIXED quality motif** (insert passing tones/ornaments at chosen points, sequence/transpose, invert, augment, vary rhythm of the same contour) over a planned harmony with real cadences — NOT free sampling. The model should only supply the motif's SURFACE flavour; STRUCTURE (motif + bounded development) must be imposed externally. Recommended future direction = structure-first (form + functional harmony + cadences + ONE motif developed) + optionally phrase-recombinance (Cope/EMI) from the corpus, with Markov only for micro-variation. (Claude hand-composed `ghibli_lullaby.mscx` + `ghibli_romance.mscx` (violin+piano, intro/theme/handoff/development→climax/outro) via compose_ghibli*.ps1 → MuseScore .mscx in the MuseScoreExporter format, as a demo of the structure-first approach the user liked.)

**Root cause (diagnosed, not the model's fault):** [BaseComposerV3.GetNote](MusicTracker/Engine/ComposerV3/BaseComposerV3.cs) uses the learned melody model on only a MINORITY of notes — strong beats are forced to `NearestChordTone` (~line 596), approach-to-chord-change notes are forced to step (~607), only weak interior notes sample the learned n-gram (~613). And melody RHYTHM was a single reused 2-cell motif (`GeneratePhraseMotifRhythm`), not the trained chain. So heuristics flatten the style. (Confirmed by [[melody-chord-degree-context]] ablation: prediction is dominated by the melodic n-gram; harmony is secondary.)

**Prioritized strategies (effort-ranked):** #1 rhythm from the trained RhythmCell chain (not a reused motif); #2 let the model decide pitch on strong beats too (soft chord-tone bias, not hard nearest-chord-tone); #3 decode the phrase by beam/Viterbi under the model (reuse MelodyResolverV2) with sampling for diversity; #4 relax pitch clamps (±7, scale-snap, ~lines 632-633) that erase idiomatic leaps; #5 higher Markov order + couple pitch↔rhythm. **Validation idea: a "style distance" metric** — compare generated vs corpus histograms (degree transitions, rhythm cells, intervals) via KL/L1, so changes are judged by a number, not just the ear.

**#1 DONE — HYBRID BOUNDED rhythm (validated win).** `GenerateMelodyRhythm` now samples the trained RhythmCell chain but BOUNDS it: a "-" beat extends the held note only up to `MaxHold=2` consecutive beats, an all-rest cell only up to `MaxRest=1`; past the cap (or with nothing sounding) it forces a NOTE-bearing cell (`PickCellNoteBearing` + `IsAllRest` helpers). This kills the runaway-"-" self-loop. `UseMotifRhythm` defaults FALSE = hybrid (TRUE = old motif). Built into bin\Debug.

**⚠️ The metric was BROKEN until 2026-06-19 — all earlier chain/motif numbers were noise.** `StyleDistanceV3.MelodyPart` picked the highest-mean-pitch part = a sparse ~6-note **Glockenspiel** decoration sitting above the real 149-note Hautbois melody. FIXED with a density gate (`notes >= max(16, maxNotes/5)`). Diagnosed by dumping `ComposeInMemory` parts (note: V2Piece/Part/Note expose FIELDS not properties → reflection needs GetField).

**Validated result (Ghibli, 8 seeds, REAL melody ~193 notes/piece):** hybrid vs motif — rhythm-cells **75.5% vs 55.2%** (big win; hybrid "-"=36% matches corpus 35%, motif over-emits 8+8 40% vs corpus 13%), degree 83.4 vs 82.3, bigram 61.0 vs 62.8 (tied). So the hybrid clearly wins on rhythm fidelity and ties on pitch.

**Style-distance metric** = [StyleDistanceV3.cs](MusicTracker/Engine/ComposerV3/StyleDistanceV3.cs) + [style_distance.ps1](style_distance.ps1): K pieces → melody histograms (degree vs DegreeHistogram, bigram vs Melody "d1" tier, rhythm-cell vs RhythmCell marginal) compared by intersection overlap%; `compareMotif` shows chain-vs-motif. **Judge every future generator change with it.**

**#2 DONE — model-driven PITCH (the same technique applied to notes), result = ~NEUTRAL (slight metric regression).** [BaseComposerV3.cs](MusicTracker/Engine/ComposerV3/BaseComposerV3.cs) GenerateLine: replaced the hard `NearestChordTone` strong-beat + approaching-change heuristics with sampling the learned chord-conditioned melody distribution EVERYWHERE, biased toward chord tones (`boost` strong=3/approach=2; `biasPcs`=cur or next chord). Metric (Ghibli 8 seeds): degree 83.4→80.3, bigram 61.0→59.7, rhythm ~75→78 (noise). Raising boost ×3→×6 didn't recover (80.9/59.9). So the OLD heuristic (force chord tone on strong beats + model on weak) already matched the corpus PITCH distribution near-optimally; pushing the model onto strong beats slightly hurts the metric — BUT the metric only scores distribution match, not perceived VARIETY (the heuristic can sound formulaic). It's an EAR call. Currently kept IN bin\Debug at boost=3 for the user to judge; revert = restore the NearestChordTone strong/approaching branches. **Takeaway: rhythm was the real lever (#1); pitch was already well-handled.**
Other lever: re-enable Ghibli's now-commented MakeMelodic/Ornament on top of the dense base (ornaments need short notes, which the hybrid #1 now provides).

**MELODY↔ACCOMP COORDINATION — DONE (2026-06-19).** With the arpeggio (LearnedAccomp) spelling the chord out, the melody clashed: (a) #2 lets the melody pick non-chord strong-beat notes, (b) the FORM reuses the theme over DIFFERENT chords — reharmonized reprise (themeA over reprProg) and transposed development (varMat over devProg) — which the arpeggio exposes. Fix = `SnapMelodyToHarmony()` post-pass in RunCompose (after Arrange, guarded by LearnedAccomp): for every STRONG-beat melody/counter note (parts 0,1), snap it to the nearest pitch whose pitch-class is actually sounding in its bar's accompaniment+bass (parts 2,3); weak/passing notes stay free. Plus a generation-time strong-beat `NearestChordTone` snap in GenerateLine. Snap condition was later widened from strong-beats-only (`% (2*Beat)`) to EVERY beat onset (`% Beat`) at the user's request — off-beat notes stay free as passing tones. Clean validation (ON-BEAT consonance): 70.3% (no snap) → 100% (every-beat snap). NOTE OutNote is a CLASS (mutating n.Pitch in foreach persists). Reflection diag: V2Piece fields not properties; AND a PowerShell gotcha — `[int]($a/$b)` ROUNDS (1.5→2) while C# integer div TRUNCATES, so a consonance diag must use `[math]::Floor` for bar index or it mis-scores ~25% (my earlier 45.8%/85% figures were that bug, not real).

**ACCOMPANIMENT — DONE (2026-06-19).** Ghibli played block chords (its RenderBarInStyle used chordal styles ChordMorph/FakeHarmonicRhythm/OpenVoicing/GrandChords; `LearnedAccomp` defaulted false). Set `LearnedAccomp = true` in [GhibliComposerV3.Configure](MusicTracker/Engine/ComposerV3/GhibliComposerV3.cs) → accompaniment now from the corpus `AccompCell` (onset rhythm) + `AccompTone` (chord-tone-index pattern), realized by `RenderLearnedAccompBar` as a SEQUENCE OF SINGLE NOTES = the learned ARPEGGIO, not stacked chords. Verified: the 'Cordes' accomp part is blockShare=0% (fully sequential), ~248 notes/piece. Texture is now melody + counter + arpeggiated strings + sustained bass. (Metric only scores MELODY, so this was verified by the block-share diag + by construction it reproduces the corpus accompaniment stats.) The flag is Ghibli-only; Vivaldi/Bach still gate on their own.

**ACCOMP PITCH MODEL ALIGNED TO THE MELODY (2026-06-19).** `AccompTone` was thin (order 3, context = func + a1). Brought up to the melody's method: order default 3→8 + a back-off ladder conditioned on the EXACT current chord degree (`cdeg`), function (`func`) and metric position (`metric`): tiers `a1|cdeg|metric, a2|a1|metric, a1|func|metric, a1|cdeg, a1|metric, a1, ""` (pure a8..a3 n-grams + these). Kept the chord-tone-INDEX token (re-voiceable + always consonant — don't switch to absolute degrees). Changed in AccumAccompTone (analyzer, +barSlices/beatSlices params) AND RenderLearnedAccompBar (generator, metric from onset pos, cdeg from cell.Root) — byte-identical labels. Re-analyzed all 5 models (now ~27MB; verified tier `a1|cdeg|metric` present; generation runs). NOT YET done (phase 2): the chord NEIGHBOURHOOD pdeg/ndeg/nfunc (what the melody has) needs threading the section `prog`+bar through RenderAccomp→RenderBarInStyle→RenderLearnedAccompBar across 4 composer files. Accomp RHYTHM (AccompCell) was already identical to the melody rhythm (order 8, c1..c8+bp).

**SECTION-AWARE RHYTHM (2026-06-19).** Both rhythm models (melody `RhythmCell` + accomp `AccompCell`) now condition on the SECTION role (`sec` = intro/theme/body/climax/outro) on top of c1..c8 + bp — so intro/outro vs climax get different rhythmic profiles. Ladder tiers added: `sec|bp|c1, c2|c1, sec|c1, c1, sec|bp, bp, ""` (byte-identical in analyzer `AccumRhythmCells` [+roleOf param] and generators `GenerateMelodyRhythm`/`GenerateCellRhythm` [+section param]). Section supplied: melody via GenerateLine's `section`; accomp via new field `AccompSectionRole` set per section in GhibliComposerV3.Arrange (intro/theme/theme/climax/body/outro). Re-analyzed all 5. Rhythm-cell overlap 75.5% → 78.2% (best yet); cell distribution now matches corpus closely (`- 39%/35%`, `8+8 13%/13%`, `q 11%/11%`). `GeneratePhraseMotifRhythm` (motif fallback) left on the non-sec subset tiers (still valid). Bach prelude GenerateCellRhythm passes "body".

**CHARACTER-CONDITIONED melody+rhythm (2026-06-19).** To let the model "distinguish movements" without a redundant new dimension: the existing CHARACTER axis (enjouée/modérée/calme/majestueux — already per-piece via MelodyCharacter + CharacterDistribution) is now PREPENDED onto the section token FOR THE MELODY + RHYTHM models only: `sec = character + "/" + role`. Analyzer: `secOf = character + "/" + roleOf(b)` (CorpusAnalyzerV2, used for melody `sec` + the two AccumRhythmCells calls; harmony/texture/dynamics/SectionRole keep plain roleOf). Generator: melody ladder + GenerateMelodyRhythm + accomp GenerateCellRhythm + Bach prelude now use `character + "/" + section` (the composer's chosen character field, set by PickCharacter in Configure). Re-analyzed all 5; rhythm-cell overlap 78→72% (the character prefix adds specificity at a sparsity cost — back-off handles it). (User reminder: don't invent a "movement" dim — reuse this character axis.) Deployed to bin\Debug.
